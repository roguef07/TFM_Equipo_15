Enunciado del Proyecto Final de Asignatura
1. Contexto del Proyecto: Arquitectura Cloud aplicada al TFM del grupo
Cada grupo, en el marco de su Trabajo Fin de Máster (TFM), deberá analizar las necesidades tecnológicas de su proyecto de investigación y plantear una solución de Business Intelligence y Big Data apoyada en servicios cloud.
Actualmente, la construcción de este tipo de soluciones puede verse condicionada por aspectos como:
Procesos o fuentes de datos heterogéneas: La información puede proceder de distintas fuentes, formatos o sistemas, lo que dificulta su integración y explotación analítica.
Limitaciones de escalabilidad y rendimiento: A medida que crece el volumen de datos o la complejidad del análisis, una solución local o tradicional puede generar cuellos de botella en el procesamiento y en la disponibilidad de la información.
En este contexto, el grupo deberá proponer una evolución hacia una Arquitectura Cloud-Native, valorando el paradigma de Data Lakehouse y la separación eficiente entre el almacenamiento masivo (Data Lake) y el cómputo analítico (Data Warehouse), siempre que resulte coherente con el enfoque de su TFM.
Como equipo de Data Engineers, vuestra misión es doble: diseñar la arquitectura Cloud más adecuada para vuestro TFM y construir un Producto Mínimo Viable (MVP) funcional que permita validar la viabilidad técnica de la propuesta.
2. Objetivos del Proyecto
El proyecto se estructura en dos fases de entrega obligatoria, diseñadas para evaluar tanto la comprensión conceptual de arquitecturas cloud-native como la habilidad práctica en la construcción de pipelines de datos.
Fase 1: Diseño de Arquitectura Cloud (Teórico)
El objetivo es diseñar la arquitectura óptima para TechRetail, asumiendo una migración completa a un proveedor de nube pública (a elegir: AWS o Google Cloud Platform).
Entregables de la Fase 1
Diagrama de Arquitectura:
Un diagrama profesional (creado con herramientas como Draw.io, Lucidchart o similares) que visualice el ciclo de vida completo del dato, desde la ingesta de las fuentes OLTP/Logs hasta el consumo final por la herramienta de BI (ej. Tableau/PowerBI).
Justificación Tecnológica:
Un documento que explique de forma concisa la elección de cada servicio Cloud.
Se debe argumentar la importancia de la separación entre sistemas OLTP y OLAP.
Se valorará el uso de servicios gestionados (DBaaS, Serverless) frente a la infraestructura tradicional (IaaS).
Estimación de Costes (High-Level):
Identificar los servicios que generarán el mayor coste (ej. almacenamiento mensual vs. coste por query analítica).
Explicar las estrategias arquitectónicas aplicadas para minimizarlos (ej. uso de formatos columnares como Parquet, particionamiento de datos, etc.).
Fase 2: Prototipo Funcional MVP (Práctico - Cloud-in-Local)
Para demostrar la viabilidad técnica y evitar incurrir en costes cloud iniciales, se construirá un pipeline funcional de extremo a extremo utilizando la estrategia "Cloud-in-Local". Todo el entorno debe ser reproducible mediante Docker.
Se proporcionará un dataset simulado en formato CSV (ej. registros de ventas y clics).
El pipeline debe automatizar los siguientes pasos:
Etapa del Pipeline
Herramientas
Resultado Esperado
1. Capa Raw (Ingesta)
LocalStack
Subida automatizada de los archivos CSV crudos a un bucket S3 simulado.
2. Procesamiento y Capa Gold
PySpark
Script que lee los datos crudos desde LocalStack, realiza una limpieza básica (tratamiento de nulos) y agrega las ventas por fecha y categoría. El resultado se guarda en S3 simulado en formato Parquet.
3. Capa Serving (Data Warehouse)
Python/SQLAlchemy
Script que ingesta los archivos Parquet procesados hacia una base de datos relacional simulada en PostgreSQL (desplegada vía Docker), actuando como Data Warehouse.
4. Consumo (Data Mart)
Archivo SQL
Creación de una tabla o vista final en PostgreSQL optimizada, lista para ser conectada a un dashboard de BI.
Requisito de Entorno: Todo el entorno de desarrollo debe ser reproducible mediante la provisión de un archivo docker-compose.yml que levante todas las dependencias (LocalStack, PostgreSQL, entorno Spark, etc.).
3. Requisitos Opcionales (Bonus - Nivel Experto)
Para los grupos que aspiren a la máxima calificación, se valorará la integración de los siguientes elementos, demostrando un nivel avanzado en ingeniería de datos:
Orquestación Continua: Despliegue de los scripts de Python y PySpark en contenedores gestionados por un clúster local de Kubernetes (minikube).
Automatización: Encapsular el flujo completo del pipeline (Ingesta → Spark → PostgreSQL) utilizando un DAG de Apache Airflow, asegurando que el proceso se ejecute de forma programada y robusta.
